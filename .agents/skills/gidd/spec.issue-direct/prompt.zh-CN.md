# Issue + 直接交付

## 1. 明确关联的 Issue

修改前明确关联的 Issue，读取其目标、范围与验收条件。
读取 gidd.link spec.issue-direct.issue 返回的表单，创建或更新 Issue 时遵循字段顺序、标题、必填要求和填写说明。
按表单标题组织 Markdown 正文，填写实际任务内容，将可验证的验收条件写成勾选条目；替换预填示例，不留占位文字。
已有 Issue 就复用；需要新建时，用 Issue 模板补齐内容后创建。
不要为同一任务重复建 Issue。

## 2. 确认目标分支

确认交付目标为该仓库的默认分支。
允许直接在目标分支提交，不要求开发分支、PR 或独立审批。
本地默认分支记录可能过期；无法确定时查询 GitHub，不猜测为 main，也不把当前分支当作默认分支。

## 3. 实现与验证

按 Issue 范围完成修改，保留用户已有改动。
对照每条验收条件自查，执行与改动相关的测试，记录通过、失败和未验证事项。
自行检查 Issue 内容是否完整、符合表单结构，以及范围是否发生变化；需要时更新 Issue。

## 4. 提交与推送

在用户授权的范围内提交和推送；提交消息关联 Issue（例如 Refs #123）。
操作前检查分支、工作区和远程最新状态，遵守远程现有保护；拒绝推送时先处理原因，不强推、不绕过规则。
用户要求“不要提交”或“不要推送”时，停在对应步骤之前。

## 5. 记录交付结果

交付后在 Issue 中记录远程提交标识、验证结果和剩余事项。
只有目标分支已接收改动且所有验收条件满足，才能关闭 Issue；本地创建提交不代表完成交付。
部分完成时保持 Issue 打开，避免提前使用 Closes/Fixes。

## 说明

当前命令只读取配置并提供指引，不执行提交、推送、Issue 写入、授权或远程规则安装，也不代表远程权限已验证。
远程操作前按 doctor 提示检查环境；写入操作只在当前任务已授权时执行。
Git/gh 原生命令不会替你强制执行这套规范。
